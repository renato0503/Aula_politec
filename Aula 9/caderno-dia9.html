§ 1

Boas-vindas à última etapa

Este é o caderno que fecha o curso. Até aqui, cada grupo construiu um MVP funcional, com telas, dados fictícios, testes e um repositório no GitHub. A partir de agora, o trabalho continua com vocês: o professor entrega o projeto, e cada equipe assume a integração com o setor, o aceite e o piloto.

O caderno não ensina a programar do zero. Ele ensina a continuar um projeto que já funciona: baixar, abrir, entender, alterar, testar, versionar e devolver pelo GitHub.

A regra de ouro

O index.html é gerado. Edite src/, app.json, nucleo/, exemplos/ e modelos/. Depois rode python construir.py.

O que você leva21 pacotes individuais em Aula 9/pacotes/, um por app, com o repositório, o que falta, o passo a passo de integração, os comandos de teste e a mensagem de commit.

§ 3

O contrato da continuidade

Cada grupo recebe um app que já funciona. O compromisso é não recomeçar do zero e não estragar o que já passa nos testes. O contrato tem cinco itens.

  • O app continua abrindo offline e sem requisição de rede.
  • O index.html continua sendo gerado pelo construir.py.
  • Os dados fictícios continuam separados dos dados reais.
  • Toda alteração entra por branch e Pull Request, com teste.
  • O aceite e o piloto ficam registrados no repositório.
Quando
Use este contrato na primeira reunião com o setor.
Por que
Ele separa o que é demonstração do que é uso real.
Exemplo na POLITEC
Um app que passa nos testes, mas usa CPF real no seed, não está pronto.
Não façaNão copie o index.html para editar à mão, não suba o ZIP com dados de produção e não faça commit de token, senha ou planilha com nome de servidor.

§ 6

Baixar o projeto: ZIP ou clone

Há dois caminhos. O ZIP é mais simples para abrir e ler. O clone é o caminho certo para quem vai alterar e devolver.

ZIP

No repositório, clique em Code > Download ZIP. Extraia em uma pasta curta. O ZIP não traz o histórico do Git, então não serve para push direto.

Clone

No terminal, rode git clone URL. O clone traz o histórico, a branch e a ligação com o GitHub. É o caminho recomendado para a continuidade.

  • git clone https://github.com/renato0503/adiantamento.git
  • cd adiantamento
  • git status
  • git branch --show-current
ZIP e GitSe você baixou o ZIP e quer enviar alterações, não rode git init no meio da pasta antiga. Clone o repositório em uma pasta nova e copie para lá apenas os arquivos que você alterou.

Todos os apps seguem a mesma arquitetura: um único HTML gerado, CSS e JavaScript embutidos, IndexedDB e dados fictícios. A pasta é pequena e tem sempre os mesmos arquivos.

§ 16

Como pedir ao agente do Antigravity

O agente é útil quando recebe contexto e um limite. Pedido vago gera alteração grande e difícil de revisar.

Pedido ruim

“Melhore o app”. O agente não sabe o que falta, mexe em tudo e você não consegue revisar.

Pedido bom

“Leia o sprint.md. Na tela #/painel, adicione o botão Avisar. Não altere o index.html. Rode os testes e mostre o diff.”

  • Leia README.md, PREMISSAS.md e sprint.md.
  • Não edite index.html.
  • Trabalhe apenas nesta tarefa: <descreva uma tarefa>.
  • Antes de alterar, rode python construir.py e os testes.
  • Depois de alterar, rode os testes de novo, mostre o diff e explique o que mudou.
Arquivos de contextoSempre peça para o agente ler README.md, PREMISSAS.md, sprint.md e o arquivo de src/ que será alterado.
§ 17

O que cada teste verifica

O projeto tem dois níveis de teste. O primeiro confere a estrutura. O segundo usa a tela como uma pessoa usaria.

ComandoO que verificaQuando rodar
python testes/testar.pyZero rede, rotas, tema, dados fictícios, #/testesSempre
python testes/cenarios.pyUm cenário por sprint, com o “Pronto quando”Antes do PR
python Apps/_base/testar.pyTodos os apps, no repositório do cursoSó no computador do professor

Teste que passou não é desculpaO teste cobre o que foi escrito. Se você mudou uma regra, acrescente ou ajuste um cenário. Teste sem cenário novo não prova a regra nova.

Se o teste falhar, leia a primeira linha do erro. Corrija uma coisa, rode de novo. Não tente “consertar” o teste para ele passar se a regra está errada.

§ 18

Dados fictícios, backup e LGPD

Os apps usam dados fictícios. O uso real exige cuidado com dado pessoal, retenção e acesso.

  • O seed não tem nome, CPF, foto ou endereço de pessoa real.
  • O backup é feito em Configuração e guardado em local controlado.
  • O app avisa a finalidade e o prazo de retenção.
  • O perfil vê só o que precisa.
  • A exclusão de um caso mantém apenas a contagem, quando a regra pede.
NuncaNão suba planilha real, print de tela com nome, backup de produção ou token para o repositório público. Se precisar testar, use o seed ou anonimize antes.
Quando
Use o botão de backup antes de cada reunião.
Por que
Se o navegador limpar os dados, o backup é a única cópia.
Exemplo na POLITEC
O backup é um .json que pode ser restaurado em Configuração.

§ 50

Revisão de código em 10 minutos

A revisão não é para achar culpado. É para garantir que o app continua funcionando e que a mudança é compreensível.

  • O Pull Request tem uma tarefa só.
  • O commit não inclui dado real, token ou backup.
  • O index.html foi gerado, não editado à mão.
  • Os testes passam.
  • O cenário novo cobre a regra nova.
  • O README ou o sprint foi atualizado.
  • A mensagem de commit explica o porquê.
Comentário útilDiga o que observar e por quê. “Aqui o prazo pode ficar negativo; teste o caso de hoje” ajuda mais do que “está errado”.

Se a mudança for grande, peça para dividir em duas. Pull Request pequeno é revisado em minutos; grande fica parado.

§ 52

O piloto e a linha de base

O piloto mede o app no uso real, com um grupo pequeno e por tempo limitado. A linha de base é o tempo ou o erro antes do app.

MomentoO que medirComo registrar
AntesTempo, erros, retrabalhoPlanilha ou print
DuranteUso, dúvidas, falhasDiário de bordo e issues
DepoisGanho, custo, satisfaçãoRelatório de 1 página
Quando
Use o piloto para decidir, não para defender o app.
Por que
Se o app não reduzir o tempo ou o erro, o piloto mostra e vocês ajustam.
Exemplo na POLITEC
Três unidades ou uma turma reduzida são suficientes para começar.
Piloto sem baselineSem o “antes”, o “depois” não prova nada. Meça uma semana antes de ligar o app.
§ 53

O que entregar no fim

A entrega final tem quatro provas: o app, o repositório, o aceite e o relatório do piloto.

  • App publicado e abrindo no navegador.
  • Repositório com README, PREMISSAS, sprint e modelos atualizados.
  • Pull Requests revisados e mergeados.
  • Roteiro de aceite assinado ou registrado.
  • Relatório do piloto com a linha de base.
  • Backup dos dados fictícios e dicionário de dados.
  • Apresentação de 5 minutos com problema, solução, número e próximo passo.

A apresentação não precisa mostrar código. Precisa mostrar o problema, o antes, o depois e o que o setor ganhou.

5 minutosUm slide de problema, um de solução, um de número, um de próximos passos e um de equipe. O resto é conversa.

Glossário

MVP
Menor versão do produto que resolve o problema principal e pode ser testada.
Repositório
Pasta versionada no GitHub, com histórico de commits.
Branch
Linha paralela de trabalho, usada para isolar uma alteração.
Commit
Registro de uma alteração, com autor, data e mensagem.
Pull Request
Pedido para juntar uma branch na main, com revisão.
Issue
Tarefa, erro ou dúvida registrada no GitHub.
Build
Processo que gera o index.html a partir das fontes.
Seed
Dados fictícios com semente fixa, usados nos testes e na demo.
IndexedDB
Banco do navegador onde o app guarda os dados locais.
Offline first
O app funciona sem internet e não faz requisição de rede.
Aceite
Confirmação do setor de que o app atende ao critério combinado.
Piloto
Uso real, limitado e medido, antes da implantação.
Linha de base
Medida do processo antes do app, para comparar depois.
LGPD
Lei de proteção de dados: finalidade, acesso, retenção e segurança.
